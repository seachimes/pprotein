# ベンチのスコアを計測に紐づける

スコアはベンチの出力にしか存在せず、pprotein は関知していなかった。そのため
「この計測結果はスコアいくつの走行か」を時刻で突き合わせる必要があり、
「速くなったか」は言えても「勝てたか」には答えられなかった。

## 記録する

走行が終わったらスコアを POST する。

```sh
curl -X POST http://localhost:9000/api/score \
  -H 'Content-Type: application/json' \
  -d '{"Score": 18902}'
```

`GroupId` を省略すると直近の成功した収集に紐づく。スコアを知っているのは
ベンチ出力を見ているシェルだが、シェルは pprotein が内部で生成した
`GroupId` を知らないため、通常はこれで足りる。

ベンチを連続で回すなど取り違えたくない場合は、明示的に指定する。
`GET /api/group/collect` は開始した収集の `GroupId` を返すので、
アプリ側で保持しておけば渡せる。

```sh
curl -X POST http://localhost:9000/api/score \
  -H 'Content-Type: application/json' \
  -d '{
        "GroupId": "2026-09-22_14-56-34.788468",
        "Score": 18902,
        "Passed": true,
        "Target": "isu1",
        "ErrorCount": 3,
        "Raw": "{\"pass\":true,\"score\":18902}"
      }'
```

| フィールド | 既定 | 内容 |
| --- | --- | --- |
| `Score` | 0 | スコア。大きいほど良い1本の数値 |
| `GroupId` | 直近の収集 | 紐づける収集 |
| `Label` | `bench` | 表示用のラベル |
| `Passed` | `true` | 走行が成功したか。**失敗も記録する** |
| `ErrorCount` | 0 | ベンチが報告したエラー件数 |
| `Target` | | 対象ホスト |
| `StartedAt` / `FinishedAt` | | 走行区間 |
| `Raw` | | ベンチの生出力 |

失敗した走行も記録する。どの変更でベンチを壊したかは、どの変更で速く
なったかと同じくらい重要なため。

スコアの表現は大会ごとに違う。合計だけの回もあれば、減点内訳が出る回も
ある。`Score` の数値1本に落とさず `Raw` に生出力を残しておくと、後から
読み返せる。

### ベンチスクリプトに組み込む

スコアの取り出し方は大会ごとに違うので、その1行だけ書き換える。

```sh
OUT=$(./bench)
SCORE=$(echo "$OUT" | grep -oP 'score: \K\d+')
curl -sX POST http://localhost:9000/api/score \
  -H 'Content-Type: application/json' \
  -d "$(jq -n --argjson s "$SCORE" --arg raw "$OUT" '{Score:$s, Raw:$raw}')"
```

### 手で入れる

グループ一覧の各グループにスコア入力欄がある。スクリプトを直す余裕が
ない場面ではこちらを使う。

## 読む

| API | 内容 |
| --- | --- |
| `GET /api/score` | 一覧。`Message` に `score=18902 pass` の要約が入る |
| `GET /api/score/:id` | 個別の記録 |

差分ビューでは、スコアが両方の走行に記録されていれば全体サマリの先頭に
出る。

## 判定への影響

競技で正解を決めるのはスコアだけなので、スコアがあればレイテンシより
優先して改善/悪化を判定する。

とくに「速くなったのにスコアは下がった」場合は悪化と表示し、警告を出す。
ベンチが失敗しているか、整合性チェックに引っかかっている可能性が高い。
レイテンシだけを見ていると成功と誤読する場面で、この機能を入れる理由に
あたる。

失敗した走行はスコアが0になるが、これは計測値ではないため数値比較の前に
悪化と判定する。逆に失敗から回復した場合は、過去の成功走行より数値が
低くても改善として扱う。
